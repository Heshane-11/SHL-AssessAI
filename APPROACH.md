# Engineering Approach & Architecture Document
**Project:** SHL Assessment Recommender Agent

## 1. Executive Summary
The goal of this project was to construct an intelligent, conversational HR assistant capable of guiding recruiters through the selection of SHL assessments. Rather than building a naive LLM wrapper, the system was designed from the ground up as a **fault-tolerant, modular Retrieval-Augmented Generation (RAG) pipeline**. 

The architecture strictly adheres to enterprise engineering principles: statelessness for horizontal scalability, deterministic guardrails for security, and aggressive hallucination prevention to ensure complete data integrity.

---

## 2. System Architecture

The core of the system is a **Stateless Pipeline Orchestrator** built on FastAPI. The API does not rely on a backend database to maintain session state. Instead, it expects the client to provide the conversation array (`messages`) on every request.

**The Orchestrator Pipeline follows a strict order of operations:**
1. **Safety Pre-Flight:** The raw user input is validated against security rules.
2. **Intent Detection:** The conversation history is classified to determine the required service logic.
3. **Service Routing:** The request is passed to a specialized handler (Recommender, Clarifier, Comparator).
4. **Retrieval & Augmentation:** Relevant catalog data is retrieved from a local FAISS vector store.
5. **LLM Generation:** The LLM is invoked to generate a conversational response.
6. **Post-Processing & Validation:** The output is sanitized, formatted, and strictly validated against the required JSON schema.

This separation of concerns ensures that the application is highly testable and components can be swapped (e.g., changing the LLM provider) without affecting downstream logic.

## 3. Data Ingestion & Semantic Retrieval

### Automated Catalog Scraping
A custom Python web scraper (`BeautifulSoup4`) extracts assessment names, URLs, and descriptions from the SHL public catalog. To guarantee system resilience, a curated 30-item offline fallback catalog is included so the application remains functional even if the source URL changes or network connectivity drops during the build phase.

### FAISS Vector Search Engine
Traditional keyword search is insufficient for conversational queries. We implemented a local vector search engine using **FAISS** (Facebook AI Similarity Search).
*   **Embedding Model:** `sentence-transformers/all-MiniLM-L6-v2` (Chosen for its extreme efficiency and small memory footprint, ideal for CPU-bound PaaS deployments).
*   **Lazy Loading:** The FAISS index is lazy-loaded into memory only on the first API request, dramatically reducing FastAPI worker startup times.

## 4. Conversational Intelligence & Intent Routing

Instead of dumping the entire user prompt into a generic LLM, the system dynamically routes traffic based on conversational intent:

1.  **Vague Queries (`clarify_needed`):** If a user provides insufficient detail (e.g., *"I need a test"*), the orchestrator triggers the Clarifier module. It asks targeted follow-up questions. To prevent infinite loops, it tracks conversation depth and forces a "best-effort" recommendation after two vague turns.
2.  **Comparison (`compare`):** When a user asks to contrast two assessments, a targeted regex/LLM extraction isolates the assessment names. The Comparator module bypasses semantic search entirely, performs an exact lookup of the two items, and forces the LLM to output a grounded, side-by-side comparison without hallucinating features.
3.  **Refinement (`refine`):** When the user asks to modify a previous recommendation (e.g., *"Make it harder"*), the full conversation context (up to 8 turns) is passed to the LLM to build a new, highly constrained semantic query.

## 5. Security, Reliability & Guardrails

Enterprise AI applications must be defensive. We implemented a multi-layered security model:

### A. Pre-Flight Guardrails (Cost & Latency Optimization)
Before invoking the LLM, fast Regular Expressions evaluate the user's prompt. 
*   **Prompt Injection:** Attempts to hijack the system (`"ignore previous instructions"`) are immediately intercepted.
*   **Out-of-Scope Enforcement:** Legal advice, salary negotiation, and coding help are instantly blocked.
By handling these via regex, we save ~800ms of latency and eliminate unnecessary LLM token costs.

### B. Absolute Hallucination Prevention
Large Language Models are prone to inventing data. Our `validate_recommendations` function acts as an absolute firewall. The final array generated by the LLM is cross-referenced against the actual `catalog.json`. If the LLM generates an assessment name that does not perfectly match a known catalog entry, that item is silently dropped from the final JSON payload. **The user will never see a fake assessment.**

### C. Smart Offline Fallback Mode
Relying entirely on third-party APIs (Gemini/OpenRouter) introduces a single point of failure (e.g., rate limits, network outages, or exhausted free-tier quotas). 
If the LLM client fails (e.g., receives a `429 RESOURCE_EXHAUSTED` error), the application **does not crash**. Instead, the Orchestrator safely bypasses text generation, pulls the top results directly from the FAISS database, and wraps them in a friendly, hardcoded conversational response. This guarantees the API always successfully fulfills the client's request.

## 6. Edge Case Handling & Scaling

*   **Token Blowout:** Passing infinite conversation histories will inevitably cause token limits to exceed. We mitigate this by aggressively slicing the context window (`messages[-8:]`) before prompting the LLM.
*   **Malformed JSON Handling:** LLMs occasionally ignore strict schema requests. The `extract_json_from_text` utility aggressively sanitizes Markdown fences (` ```json `) and parses raw text blocks. If parsing completely fails, the system safely reconstructs a fallback schema internally.
*   **Deployment Constraints:** The entire dependency tree is optimized. `pydantic-core` and `faiss-cpu` versions were explicitly pinned to avoid source compilation requirements on Windows, ensuring seamless binary installations across Render, Railway, and local environments.
